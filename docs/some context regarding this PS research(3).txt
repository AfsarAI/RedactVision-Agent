Problem Statement Title	
On-device Visual Perception for Light-weight Browser Agents
Description	
Background AI agents are becoming omnipresent in the current era and can play an important role in our digital interactions. If an agentic AI pipeline has access to our visual context, screen states, they can assist users in complex workflows and automate many tasks. Most of the agentic AI pipelines are deployed on server side which limits the type to data that a user can share with it. It would open a new dimension of possibilities, if a local agent is deployed on user machine particularly browser which can eliminate the need to share the sensitive data with the server. Local system generally has fewer resources than server and is unable to host a full-fledged pipeline therefore only the non-sensitive data such as structure of the screen, application fields etc can be sent to server for processing.

Modern browser APIs (such as WebGPU and WebAssembly) and local inference libraries (like ONNX Runtime Web and Transformers.js) have unlocked the ability to run lightweight machine learning models directly on the client. The aim is to bridge these two environments: leveraging the reasoning power of cloud or server based AI while strictly enforcing data privacy at the client side.

Description Participants are required to build a privacy-preserving vision agent which runs on browser. This involves implementing a client-side architecture where a local Vision Transformer (ViT) or equivalent computer vision model 'reads' the user's screen and takes decision based on that. If it requires the visual context to be sent to server, it shall sanitize the sensitive/PII data using DOM tags or any other method, before any network request is made. It should dynamically detect and redact sensitive elements. For example, blurring faces, blacking out passwords, and masking PII etc. Only this anonymized, unidentifiable data should be transmitted to the central server which should be aware for this redaction scheme and can process data accordingly. The server will then process the sanitized context and return actionable commands for the browser agent to execute. Participants must balance the trade-offs between inference latency and the accuracy.

Expected Solution A successful submission should include a working prototype consisting of client side extension and server that demonstrates the following:

Client-side (extension/JS) running in popular browsers (chrome, Firefox) components:

• Local Vision Processing: Implementation of a client-side vision model running in the browser (e.g., via WebGPU) that evaluates the current screen state.
• Privacy Preserving Filter: A mechanism for sanitizing sensitive or personal visual data. This can be achieved through local bounding-box redaction, semantic obfuscation, masking etc. This should be clearly demonstrated.

Server-side implementation components:

• Server Side Integration: The transmission of the anonymized visual context to a centralized LLM/VLM, which successfully interprets the sanitized data and returns the response which may be processed data to be again ingested by local client or an UI action (e.g., 'click the submit button,' 'scroll down') that the local client executes.
• Participants are free to use any offline deployable (open-source/open-weights) model on server side. During SIH they can use cloud hosted version of these. An end-to-end task assisting the user should be demonstrated.

# SIH Problem 26171 — Deep Research & Technical Architecture Report

## 1. Executive Summary

Yeh research report **SIH Problem Statement 26171 (ISRO)** ke liye ek end-to-end technical blueprint evaluate aur present karta hai. ISRO ka core objective ek aisa **Privacy-Preserving Vision Agent** banana hai jo browser ke andar run ho Sake, user ki screen ko visually aur structurally samjhe, local machine par sensitive/PII data ko detect aur redact (mask/blur) kare, aur sirf anonymized context server-side Vision-Language Model (VLM) ko bheje.

Humara proposed system **Hybrid DOM + Accessibility Tree + Lightweight Visual OCR/Object Detection** approach par kaam karta hai. Client side par **WebGPU** aur **ONNX Runtime Web** ka use karke ultra-fast local inference implement kiya gaya hai, jabki server-side par **Qwen2.5-VL-7B-Instruct** model high-level action planning handle karta hai.

## 2. Problem Statement Explained in Simple Hinglish

### Simple Explanation

Aajkal AI agents computer aur browser par humare kaam aasan bana rahe hain (jaise forms bharna, flights book karna, ya workflow automate karna). Lekin problem yeh hai ki in agents ko kaam karne ke liye humari screen dekhni padti hai.

Jab ek normal AI agent screen ka screenshot server par bhejta hai, toh screen par dikhne wala sensitive data—jaise passwords, email addresses, phone numbers, banking details, confidential documents, aur faces—bhi server par chala jata hai. Yeh ek bahut bada **privacy risk** hai.

ISRO ka requirement yeh hai ki hum ek aisa **browser extension agent** banayein jo:

1. Client-side (user ke browser ke andar) screen ka analysis kare.
2. Sensitive PII (Personally Identifiable Information) ko **locally redact** (blur ya black-out) kare.
3. Server ko sirf **sanitized/anonymized** screen state bheje.
4. Server se reasoned action commands (e.g., "Click Submit") receive karke local browser mein execute kare.

```
[ User Screen ] 
       │
       ▼
[ Client Extension (WebGPU + Local Privacy Model) ]
       │  (Redacts Passwords, Emails, Faces)
       ▼
[ Sanitized Context / Masked Image ]
       │  (Sent over Network)
       ▼
[ Server VLM (Action Planning) ] ──> Returns JSON Action ──> [ Client Executes Action ]

```

## 3. Why This Problem Matters

1. **Enterprise & Defence Data Security:** ISRO jaisi strategic organizations internal tools aur dashboards mein cloud-based agents use nahi kar sakti kyunki proprietary screen data leak hone ka khatra hota hai.
2. **Regulatory Compliance:** GDPR, DPDP Act 2023 (India), aur HIPAA guidelines strict demand karti hain ki PII (Personally Identifiable Information) bina user consent ke server/third-party AI provider ko na bheja jaye.
3. **Zero-Trust Client Compute:** User side par dynamic redaction se third-party server compromise hone par bhi user ka private data safe rehta hai.

---

## 4. Core Pain Points

### A. Core Technical Problem

Kaise ek ultra-lightweight AI pipeline ko browser environment mein **< 100ms latency** mein run karein, jo **> 95% PII detection recall** achieve kare aur browser CPU/RAM resources ko exhaustion se bachaye?

### B. Current Architecture Problem

Existing commercial computer-use agents (jaise Anthropic Computer Use, Operator, Browser-Use) full-resolution raw screenshots ko direct cloud LLMs (GPT-4o, Claude 3.5 Sonnet) par bhejte hain. Isme zero privacy guarantees hoti hain.

### C. On-Device Constraint

User ke device par full VLM (e.g., 7B parameters) run nahi kar sakte kyunki:

* **VRAM Limitations:** Normal laptops/desktops ke paas 8GB–16GB system RAM hoti hai, Dedicated VRAM nahi hoti.
* **Browser Sandbox Limits:** WebAssembly (Wasm) ki memory limit typically 4GB per tab hoti hai.
* **Battery & Latency:** Browser tab mein heavy matrix multiplication laptop battery ko fast drain karti hai.

### D. Privacy Leakage Risks

Blindly sending screenshots leaks:

* **Textual PII:** Email IDs, Phone numbers, Credit Card numbers, Addresses.
* **Visual PII:** Profile pictures, webcam video streams, government ID cards.
* **Session Tokens:** API Keys, Bearer tokens, cookies visible in devtools/URL.

### E. Agent Reliability Problem

Screen coordinates-only based execution fragile hoti hai (screen resolution ya scaling change hone par click miss ho jata hai). AI agent ko unique DOM selectors aur Accessibility Tree nodes ki zarurat hoti hai.

* **Hybrid Context Transmission:** Raw image ki bajaye, Sanitized Image Crops + Structurally Pruned DOM Tree bhej kar network footprint 80% reduce kiya jata hai.

## 9. Browser Extension Architecture (Manifest V3)

Manifest V3 restrictions ko handle karne ke liye component design:

1. **Content Script:** Webpage ke DOM mein inject hota hai. HTML elements, input fields, attributes parse karta hai aur final action execute karta hai (e.g., `.click()`, `.value = '...'`).
2. **Background Service Worker:** Event routing, state management, aur server-side communication Handle karta hai.
3. **Offscreen Document:** Service workers mein Canvas API / WebGL availability restricted hone ke karan, Offscreen Document dedicatedly **WebGPU context** aur **ONNX Runtime Web** execution host karta hai.
4. **Popup UI:** User controls, privacy logs, sensitivity level threshold settings, aur authorization prompts.

## 10. Local Vision Pipeline

Client side par heavy screen processing ke liye ultra-fast local vision models:

* **WebGPU Integration:** `onnxruntime-web` (WebGPU backend) or `@huggingface/transformers` (Transformers.js v3). WebGPU GPU-accelerated matrix multiplication directly browser ke inside enable karta hai.
* **Model Choices:**

## 11. Privacy / PII Detection Pipeline

Multi-layer approach high **Precision (20%)** aur **Recall (20%)** guarantee karta hai:

```text
[ Raw Screen Inputs ]
        │
        ├── Level 1: Deterministic DOM Parsing (Latency: ~2ms)
        │     └── Password inputs, autocomplete, attributes, hidden tokens
        │
        ├── Level 2: Regex & Heuristic Engine (Latency: ~5ms)
        │     └── Email, Phone, Credit Cards, Government Identifiers
        │
        ├── Level 3: Local Transformer NLP/NER (Latency: ~35ms)
        │     └── Names, Organizations, Addresses in unstructured text
        │
        └── Level 4: Computer Vision / Face & Card Detector (Latency: ~40ms)
              └── Faces, Profile Photos, Physical Document Cards
        │
        ▼
[ Aggregated Sensitive Bounding Boxes & Text Nodes ]

```

### Multi-Layer Mechanisms

1. **Deterministic DOM Rules:** Elements matching `input[type="password"]`, `[autocomplete="cc-number"]`, `[aria-label*="ssn"]` are automatically tagged for redaction instantly without needing AI inference.
2. **Regex Engine:** Fast pattern matching for standard patterns (Emails, Phone Numbers, Financial Accounts).
3. **Local NER (Named Entity Recognition):** Quantized `bert-base-NER` running via Transformers.js for dynamic text names/locations.
4. **Visual Masking Engine:** BlazeFace / YOLOS identifies image bounding boxes containing human faces or identity card shapes.

---

## 12. Redaction Engine & Semantic Preservation

To ensure server VLM **understands context (25% weight)** while **protecting privacy (20% weight)**, we use **Semantic Replacement** instead of destructive blurring:

```text
Raw Text: "User Mohd Afsar logged in with email afsar@example.com"
        │
        ▼  (Semantic Masking)
Redacted Text: "User [PERSON_NAME_1] logged in with email [REDACTED_EMAIL_1]"

```

Visual Redaction on Screenshots:

* **Blackout Box (`#000000` fill):** Applied on credentials and private visual cards.
* **Gaussian Blur (Sigma = 15):** Applied on detected faces.
* **Bounding Box Label Overlay:** Redacted areas are labeled with synthetic tags so the server VLM recognizes an element exists without knowing its private content.

## 15. Action Representation & Grounding

Server outputs strict JSON actions adhering to a custom schema:

```json
{
  "step_id": 3,
  "action_type": "click",
  "target_selector": "button#submit-form-btn",
  "target_description": "Submit Button next to User Registration",
  "fallback_coordinates": {"x": 450, "y": 620},
  "confidence": 0.96
}

```

### Action Types Handled:

* `click`: Clicks element via selector or coordinate fallback.
* `type`: Types text into specified element.
* `scroll`: Scrolls `up`/`down` by specific pixel offsets.
* `navigate`: Redirects to URL.
* `wait`: Delays execution for dynamic network requests to finish.

## 16. Security Architecture & Threat Safeguards

```text
[ Server Action ]
       │
       ▼
[ Local Policy Engine ]
       │
       ├── Risk Level Check (Is it a high-risk action like Payment/Delete?)
       │
       ├── Prompt Injection Verification (Is page trying to trick the agent?)
       │
       └── Confirmation Protocol (Show modal to user if Risk == HIGH)
       │
       ▼
[ Browser Execution ]

```

### Key Security Protocols:

1. **Indirect Prompt Injection Defense:** Text scraped from web pages is enclosed in `<untrusted_web_content>` tags before sending to server VLM.
2. **Local Policy Engine:** Actions like `Submit Payment`, `Delete Account`, `Send Email` trigger an explicit user permission popup in extension UI.
3. **Domain Whitelisting:** Extension runs only on authorized operational domains configured by the user/organization.

## 25. Performance Optimization Techniques

* **INT8 Quantization:** Models are quantized from FP32 to INT8, reducing memory footprint by **75%** (e.g., 50MB model becomes 12.5MB).
* **Region-Of-Interest (ROI) Cropping:** Instead of feeding full 4K screenshots to local vision models, we crop active form regions and viewport frames.
* **Event-Driven Execution:** Perception pipeline executes only on DOM change events (`MutationObserver`) or user scroll/navigation, keeping idle CPU usage near **0%**.

## 4. Core Pain Points

1. **Privacy Leakage (Bahut sensitive data hota hai):**  
   *Problem:* Screen par password, email, ID, credit card number, private chat, medical info, tokens wagairah show ho sakte hain. Agar agent screenshot bhejega to sab kuch leak ho jayega.  
   *Kyu hota hai:* Cloud-based agents jo full screenshot ya DOM deta hain, sensitive field detect nahi karte by default.  
   *Difficult because:* Ye data har website me alag tareeke se hota, koi standard format nahi; aur hamesha visible bhi nahi (jaise password fields ke dots).  
   *Impact:* Data breach, identity theft, confidential info exposure.  
   *Our fix:* Local pipeline me pehle **PII detection** karke ye fields identify karenge (password fields ko DOM se, emails/phones OCR/regex se, faces via vision) aur phir **redact** kareinge. Sirf sanitized info hi server bhejnege. 

2. **PII Detection Errors (False positives/negatives):**  
   *Problem:* Sensitive info pehchanne me galti (kuch PII miss ho ya galat cheez PII samjho).  
   *Kyu hota hai:* PII patterns diverse hote (e.g. phone number alag format), text OCR me errors hote, aur images me face detection misses/false alarms hojate.  
   *Difficult:* Hamara multi-layered approach bhi complicated hai – DOM tags, regex, NER, OCR, vision sab mix karna tough hai.  
   *Impact:* **False positive:** normal text blur ho jaye, agent ko samajh me nahi ayega (usability kharab). **False negative:** koi sensitive cheez choot jaye to privacy leak.  
   *Solution:* Use hybrid detection with high precision techniques. Pehle DOM-level cues (input type=password, autocomplete, labels) se detect sensitive fields, phir regex/NER on text se (emails, phone), phir OCR on images, face detector for images. Fusion karne se recall/precision badhegi. Ye ensure karega ki miss/kho jane wali PII kam se kam ho.

3. **Over-Redaction vs Under-Redaction:**  
   *Problem:* PII mil gaya, ab redact karte hain. **Over-redaction** me zaroori context nikal jata (e.g. puri field blur karne se model confuse ho sakta hai), **under-redaction** me hidden leak reh jata.  
   *Kyu:* Agar pura text blur ya black kar diya jaye to server vali model ko samajh nahi ayega screen context kaise interact karna.  
   *Difficult:* Balancing rakna bht hard – redaction me enough info remove ho jaye par action ke liye cues bache.  
   *Impact:* Over-redaction: agent kaam nahi karega (server ko patha na ho kya clickable). Under-redaction: privacy fail.  
   *Solution:* **Semantic masking** – jaise actual name ke jagah “[PERSON_NAME]” ya phone ke jagah “XXX-XX” jaisa maintain kara. Ya blur just itna jitna sensitive ho. Eg: email “abc@example.com” ko “xxx@xxxxx.com” banaye, so server samajh sake structure. Examples pe research se ye idea hua ke contextual placeholders use karo, taaki server still tasks plan kar sake.

4. **Visual Understanding & Action Grounding:**

DOM se text/content structure milega, browser-accessibility tree se element roles/ids milega, aur screenshot me jahan DOM na ho (images, canvas) wahaan vision se help le. Example: OmniParser jaisa approach dikhata hai ke vision se UI elements detect karna (YOLO se buttons find karna) aur OCR se text. Hum similar kar sakte hain par DOM ke saath. 8. **Security Risks:**  
   *Problem:* A smarter agent can be misused: malicious sites can try to trick it.

## 6. Limitations of Existing Systems

- **Privacy Concerns:** Cloud agents leak screenshot data. Even secure channels nahi guarantee privacy of on-screen info. Official note: “Modern web apps render personal data; browser extension must mask them”.  
- **Latency & Bandwidth:** Sending full screenshots (particularly high-res or multiple regions) slow. Many agents don't optimize context size.  
- **Lack of Local Context:** Server models don't see live DOM or events; they only get flat info. Koi dynamic element highlight missing.  
- **Heavy Server Load:** Cloud GPUs use high compute. If everything sent to server, cost zyada. Local inference can reduce load.  
- **Agent Reliability:** Pure vision agents can misinterpret UI. For example, without DOM, how to know which text is button? OmniParser shows naive GPT-4V can do 70% accuracy, while structured parse hits ~94%. So existing GPT agents may hallucinate on UI.  
- **Security Risks Unmitigated:** Existing openAI/Google browser tools didn’t focus on malicious actions. Our secure design will patch these.

## 7. Proposed Solution

**Humari solution:** Ek **browser extension** jisme local vision + privacy filtering + server reasoning pipeline ho. 

- *Local Perception:* Extension screenshot aur DOM leke lightweight vision model (jaise ViT/Samll DETR) aur OCR chalata hai. Ye identify karega screen ka context: field labels, buttons, text. 
- *Privacy Filter:* Screen pe se sensitive info identify karke redact kare (mask, blur, replace). Sirf anonymized info hi server ko jaayegi. DOM cues se jaise `<input type="password">` password field; regex se emails; OCR se images containing numbers or PAN; vision se faces/cards. 
- *Server-side Reasoning:* Redacted screenshot ya structured data server pe jayega. Wahan ek open VLM/LLM use karke context interpret hoga. Model ko pata hona chahiye ke `[PASSWORD]` kisi password ko denote karta hai. Fir model decide karega user intent aur next action (e.g. click login, fill name). 
- *Action Returning:* Server structured action JSON return karega. Example: `{"action":"click","target":"submit"}` or `{"action":"type","target":"email","value":"[USER_EMAIL]"}`. This is machine-friendly and precise. 
- *Local Execution:* Extension wo action execute karega. Target ko DOM selectors/accessibility nodes se map karke perform. If needed, final policy check (for security) karega; kuch critical actions user confirm karwa sakta hai.

Is process me data **lokal hi rehta** jab tak sanitized. Server sirf anonymized context pe kaam karta hai. Ye architecture design metrics (Accuracy, Privacy, Resource, Latency) pe balance karega.

```
Structured Action JSON
      │
      ▼
Local Validation (policy, confidence check)
      │
      ▼
Extension Action Executor (DOM manipulation, click, type, scroll)
      │
      ▼
Browser Effect (user sees updated page)
      ↓
User (observes result)
```

**Components:**

- **Content Script:** Web page par chalta hai, direct page context me. Ye DOM aur accessibility tree (HTML elements with roles/labels) read karta hai. Ye screenshot bhi capture kar sakta (using browser API or HTML Canvas). Content script isolates extension from page for security.
- **Local Privacy Engine:** Yeh content script ya offscreen worker ke form me chal sakta hai. Yeh DOM/JSON/text stream me PII patterns dhundta (password, name, etc.). Vaise hi, OCR run karke extracted text me regex/NER apply karta (phones, emails). Vision se faces/cards detect karta.
- **Local Vision Model:** ONNX/WebNN/Transformers.js se chala hua chhota model. Ye screenshot se UI elements (buttons, text boxes) detect karta. Example: YOLOv8N for object detection, MobileViT/EfficientNet for scene context. WebGPU backend pe inference (speed boost).
- **Context Builder:** Ye sab output (DOM elements positions, OCR text, detection boxes, sanitized image regions) ko ek combined data structure (shapes or JSON) banata. For example, DOM form fields with bounding boxes, OCR text if any, tags for redacted parts.
- **Secure Gateway:** Encrypted channel se server pe bhejne ke liye intermediate. Koi header say server ko batayega ki yeh data sanitized style me hai.
- **Server (LLM/VLM):** Received context par inference. Ye pretrained vision-language model jaisa ki LLaVA, Qwen-VL ya MiniGPT-4 (agar open weight milta ho) use kar sakta hai. Model instructions me hoga: * interpret sanitized screen -> plan user’s intent -> output action JSON*. JSON output define kiya hua schema follow karega (function calling style).
- **Structured Action Parser:** Local pe server ka JSON parse hota hai (extension service worker). Validate karta, phir target element DOM query finder ko batata.
- **Action Executor:** Content script phir actual browser me action karta: click, type, scroll, navigation, etc. Ye sab *browser APIs* se hota.

Is architecture me har component ki jagah carefully design hogi. Chrome MV3 me background *service worker* rahega jo server communication/manage karega, content script page se connect karke info lega.

## 9. Browser Extension Architecture

**Manifest V3 (Chrome/Firefox):** Ek manifest.json hogi jisme content scripts, permissions, background worker define honge. Content script pages me inject karega jaha interaction chahiye. Background service worker handle karega API calls to server (MV3 background scripts replaced by service worker).

- **Content Script:** Content script DOM access karta hai. Ye screenshot liya, DOM aur accessibility tree gaya leta, user interactions listen karta (agar we want event-driven inference). Content scripts isolate page context (isolated world) to prevent page scripts se conflict.
- **Background/Service Worker:** MV3 me persistent background page hat gaya; ab service worker runs on events. Ye messaging se content script se data lega, phir server call karega. Service worker GPU access limited, but can load WASM and maybe WebGPU (with some flags). For heavy compute, hum Offscreen Document use kar sakte.
- **Permissions:** Extension ko `activeTab`, host permissions (s3:///* for dataset if needed), screenshot capture (`chrome.tabCapture` or `chrome.tabs.captureVisibleTab`), storage, web request/permissions (if needed). 
- **WebGPU & WASM:** Content script or offscreen can use WebGPU via supported API (mostly Chrome). ONNX Runtime Web (with `webgl` or `webgpu` execution) or Transformers.js (which uses Wasm or WebGPU) me model run karega.
- **Message Passing:** Content script & background talk via `chrome.runtime.sendMessage`. For example, content sends sanitized context to service worker, which awaits action JSON back.
- **Data Flow:** Content script → (pii detection + local model) → send minimal info to background → background HTTP to server → action → back to content.

References: Chrome docs say content scripts can read page details, MV3 uses service worker instead of background pages.

## 10. Local Vision Pipeline

Browser me run karne layak lightweight vision models pe research kiya:

- **MobileViT:** Meta ka ViT variant optimized for mobile. Size chhota, GPU friendly. [CITATION needed, but from literature, it's light]
- **MobileNet/EfficientNet:** Popular image classifiers/detectors optimized for speed. ONNX me convert ho jate. ONNX Runtime Web examples include MobileNet for object detection tasks.
- **YOLO-family (Nano):** Ultralytics ne YOLOv8 ka nano version (5-10MB) banaya for low compute. Ye object detection me fast hai. Buttons/Icons detect karne ke liye fine.  
- **ViT Variants:** Standard ViT bohot heavy, lekin DeiT (Tiny or LightViT) ya DistilViT ho sakta. Vision Transformer pixel-level understanding dega (jaise layout recognition). But ensure size <100MB for browser.
- **DETR Variants:** DETR (end-to-end object detection transformer) expensive; try smaller DETR (e.g. DINO-mini).
- **CLIP-like:** CLIP/Vision-Language models (small versions like CLIP-Imageembedding) to understand context, not needed for UI.  
- **OCR Models:** Tesseract.js (browser port of Tesseract) ya PaddleOCR via WASM. We use for text extraction from images/screenshots. 
- **UI-element Detectors:** Research se milta: *UI-DETR* (Roboflow) trained on screen UIs. Or Apple’s UI Element detection networks (unpublished). OmniParser used YOLOv8 to detect UI elements.
- **Local LLM (Small):** Likely skip on-device LLM; not feasible for vision tasks on-device. 

Comparison criteria:
- **Model Size:** <=100MB best; ideally quantized to <50MB. YOLOv8n ~6MB, MobileNet ~16MB.  
- **Accuracy:** YOLO high for objects; MobileNet/EfficientNet moderate for general features. Use ensemble: e.g. UI-detection + OCR to identify form fields.  
- **Inference Speed:** With WebGPU, YOLOn can do ~20 FPS on desktop. MobileNet on WASM ~10ms per image.  
- **Browser Support:** ONNX Runtime Web with WebGPU if possible, else WASM fallback. Transformers.js supports image tasks too (like vision transformer).
- **Quantization:** All models quantizable. YOLOv8 supports INT8 export. WebGPU + ONNX web supports INT8.  
- **Implementation:** Many models on HuggingFace or Roboflow. ONNX conversion needed.  
- **Recommendation:** For PII detection (faces, cards): use a small face detector (e.g. BlazeFace ~2MB). For UI: use YOLOv8 nano or MobileNet SSD. For overall layout: lightweight ViT or CNN for scene understanding. OCR with Tesseract.js for any text extraction.

Final pick (for prototype):  
- **UI Object Detection:** YOLOv8 Nano (ONNX) for buttons/icons.  
- **Text Recognition:** Tesseract.js in browser.  
- **Sensitive Object Detection:** SSD MobileNet or face API for faces.  
- **Model Execution:** ONNX Runtime Web with WebGPU for large (if available), else WASM. Transformers.js for any required classification.

## 11. Privacy / PII Detection Pipeline

**Multi-layer detection** strategy: 

1. **DOM-based signals:** Browser DOM provides clues: `<input type="password">` clear password, `<input type="email">`, `<input placeholder="SSN">`, `name="pan"`, `aria-label="phone number"`, etc. Ye easiest aur fastest: extension iterates DOM nodes to mark sensitive fields (password fields are auto-detected). Similarly, standard attribute `autocomplete="cc-number"`, `inputmode`, etc.
2. **HTML semantics:** Element text like `<label>` with “Email” or “Phone”. Even CSS classes/id containing “pwd”, “pass”, “email”.
3. **Regex-based on text:** Agar koi plain text (copy/paste content) jaisa email@, phone formats, Aadhaar (12 digits), PAN (5 letters-4 digits-1 letter), credit-card (16 digits pattern) dikhe, regex match karke flag kare.
4. **NER (NLP) on text:** Lightweight NER models (spaCy or Transformers) to detect names, orgs. For example, if page text says “John Smith, Manager”, we might call that PII (PERSON). But NER on client is heavy; better as server check.
5. **OCR on screen:** If image (say a snapshot of eKYC document, or CAPTCHA), use OCR (Tesseract.js) to extract text. Then run regex/NER on that. This catches text not in DOM (scanned docs, infographics).  
6. **Vision-based:** Detect **faces** (Haar cascade or tiny CNN) in images/screenshots – agar face dikhe, blurred kare. Similarly credit cards or IDs via classifiers. Local models (Tiny YOLO on card images) can find these.
7. **Hybrid analysis:** Combine above: For example, if DOM says a field is password, we don’t need OCR. If OCR text in screenshot matches user’s email, but DOM didn’t show, that’s interesting.

**Pipeline flow:** Jab content script run kare, woh pehle DOM-pass karta. Password fields, masked inputs remove kar deta. Then screenshot uss page ka leke (maybe partial screenshot for relevant area) OCR chalata. Regex check karta phone/email. Vision model diya screenshot me faces or card detect kare. Har detected PII pe ek “mask tag” generate hota (like coordinate + type).  
Hum final set of sensitive regions list banayenge, to kisi duplicate redact avoid ho. Ye log send karte server ke liye bhi audit trail.

Local PII detection training/sources: Kaggle PII detection datasets (harmless, but mostly text). Also web forms data for names. Face detection pre-trained (MTCNN or RetinaFace models small). Credit card detection: pre-trained YOLO models exist.

Metrics: Precision/Recall bohot maine peche – hum ensure recall high (na koi PII chhoot jaye) and precision bhi high (na normal info redact ho). Achievable via ensemble and threshold tuning.

## 12. Redaction Engine

Sensitive info ka redaction is critical. Kayi options:

- **Blur:** Gaussian blur region. Good for privacy, but LLM sees gibberish. Server ko ye samajh me nahi aayega kya blur pe tha.  
- **Black Box:** Simply black rectangle. Extreme privacy, but server loses info about position/size maybe. Also might break visual flow.  
- **Pixelation:** Mild privacy, still unreadable, but LLM sees pattern (not ideal).  
- **Masking with token:** Replace text with placeholders. E.g. “John” → “[PERSON_NAME]” in screenshot (agar text region extract karke re-render). Or overlay image snippet that says “[EMAIL]”.  
- **Synthetic replacement:** Put fake but structured data: “XXX@YYY.com” instead of real email. Keeps format cues.  
- **DOM redaction:** Instead of image, change DOM text to [MASK] before screenshot. But screenshot already had original? Must re-capture or mask image.  
- **Semantic replacement:** For facial blur, maybe replace face area with generic silhouette icon to hint presence of person.  

Goal: Server **samajh sake ki kya click kare** even after redaction. So likely best: **token replacement** for textual PII (so model knows a name or number was there but not which). For passwords, just blank out completely (server doesn’t need content; just sees a password field). For faces, blur or replace with generic, server just knows “face was here.” Eg: redacted screen can still show a blurred shape so server knows element but no identity.

Example from instructions: “Mohd Afsar → [PERSON_NAME], 9876543210 → [PHONE_NUMBER]”. Yeh semantic masking jaisa. Web docs [14†L174-L182] mention blurring faces etc. We combine: blur faces (since vision model on server might try face recognition if not blurred), but mask text with tokens. For input fields, maybe mask their value attribute instead of image. Or if screenshot entire window, overlay labels.

Important: **Server should understand redaction scheme**. We will communicate scheme in payload (e.g. JSON that “[EMAIL]” stands for obfuscated email). Possibly always same tokens, or pass token map. 

So proposed: Use overlaid placeholders (like [EMAIL], [PHONE]) for text sensitive. For images: blur or black. In either case, keep shape/position. For example, blur face or put generic avatar image. Or pixelate sensitive image. LLM will know "there was private info here."

Citations: [14] recommends blurring faces, [45] warns that hidden instructions can come in HTML, so we must sanitize HTML too (remove scripts?). [49] shows overlay can deceive clicks – so ensure our placeholder overlays not interactive so server sees it's placeholder.

## 13. DOM + Screenshot + Accessibility Strategy

**Approaches Compared:**  
- *Screenshot Only:* + Saare visuals milte (canvas, images). - Bahut data heavy, privacy risky, visual model he rely karega (UI samajh mushkil).  
- *DOM Only:* + Lightweight (text only), easy to parse structure. - Miss images/canvas, hard to detect click coords.  
- *Accessibility Tree Only:* + Semantic roles (buttons, headings, etc.), sometimes bounding boxes. - Might miss content if page not accessible-friendly.  
- *DOM + Screenshot (Full):* + Full info (text+layout), can cross-check. - Privacy risk due screenshot, big.  
- *DOM + Accessibility + Vision:* + Hybrid: use DOM+ARIA for structured info, use vision for what's missing. Could sometimes skip full screenshot: e.g. only take screenshots of sensitive regions for OCR or faces.  
- *DOM + Accessibility + minimal screenshot:* Possibly: for each redaction, capture just that region image.

**Trade-offs:**  
- *Privacy:* DOM-only best (server gets no image). Full screenshot worst. Hybrid moderate if we send images. But our sanitization tries to minimize what server sees.  
- *Accuracy:* DOM+Vision best for understanding, DOM-only may miss UI elements in image. E.g. if button rendered via canvas, vision needed.  
- *Latency:* Less data is faster. Sending DOM JSON smaller than image.  
- *Robustness:* Pure screenshot resistant to dynamic HTML (just sees pixels), but brittle to layout changes. DOM robust if structure stable.  
- *Recommended:* **DOM + Accessibility tree + selective screenshot**. DOM/tree se majority info; screenshot only for OCR/face on detected sensitive bits. Eg: capture image regions around faces to blur, or around unknown text. This minimises data out.

For SIH, best approach is Hybrid: content script reads DOM and accessibility info (text, element roles, bounding boxes), does local analysis. Only send server *sanitized context*, which could be: structure of page (elements and text, with placeholders) plus perhaps small images of non-sensitive parts. If possible, avoid sending raw screenshot at all. But spec says "visual context", so a sanitized screenshot (privacy filtered) or the DOM structure plus redacted image is fine.  

Key: *DOM provides exact clickable targets, accessibility gives roles/label (server knows 'this is button X'), screenshot/vision fills gaps*. We’ll likely send DOM+structured info first, and if needed a sanitized screenshot segment (with PII removed).  

We must mention:
Web platform support: modern browsers have **Accessibility Object Model** (AOM) or at least `aria-` attributes for semantic info. Chrome extension can query `window.getComputedAccessibleNode(element)`. Combining screenshot+DOM is proven to work better (OmniParser improved chain-of-thought reasoning tasks with structured parse vs raw image).

## 15. Action Planning and Execution

Server output: Structured JSON with **action** field, **target identifier**, possibly **value**. E.g.: 
```json
{ "action": "click", "target": { "type":"button", "label":"Submit", "confidence":0.9 } }
```
or 
```json
{ "action": "type", "target": { "type":"input", "label":"Email" }, "value": "[USER_EMAIL]" }
```
We avoid free text replies (like “Click the login button”) because parsing is hard. Instead use something like [35†L64-L72] suggests: LLM output must be machine-readable. JSON schema ensures no ambiguity.

Ways to specify target:
- **DOM-selector:** server could identify element by known CSS path or ID from sanitized DOM. But that is brittle if page changes.
- **Accessibility id:** e.g. use `aria-label` or `automationId`. 
- **Coordinates:** [x,y] of element center. But not robust if responsive layout.  
- **Semantic label:** “the button with text ‘Submit’”.
- **Hybrid:** send target attributes from context (like field name).
We may simply use element attributes plus screenshot location.

Probably best: server returns element attributes (like `{"tag":"button","text":"Submit"}`) and extension will find matching DOM element (first visible button with that innerText). If multiple, use more info (position or form context). Also send `confidence` so local can check if it recognizes target.

For `type` actions (fill fields), server can provide value placeholder. Eg: `value:"[USER_INPUT]"` to indicate type that from context (we can even have server not output actual user data – for user-specific fields, agent will use known stored data or ask user input).

Important: We might allow *function calling* style instructions if using OpenAI, but offline model needs manual prompt structure. We'll define JSON schema with fixed keys (action, target, value, confidence).

Use references:
JSON structured agent output is best practice. OWASP doc [45] uses example. We will mention [35].

## 16. Security Architecture

Safeguards:

- **Local Policy Engine:** After server suggests action, extension checks policies. For example, do not auto-submit login without user consent (since login data privacy is high risk). If action is “type password” – better skip or ask user.  
- **Risk Classification:** Map actions to risk. E.g. navigating away = low, autofill credit card = high. Define policy: high-risk actions require confirmation pop-up. This mitigates clickjacking as user explicitly agrees.  
- **Input Sanitization:** Before feeding page content to LLM, remove malicious HTML/JS. For instance, if page has hidden instructions tags, strip HTML comments and scripts. OWASP warns hidden prompts can override LLM instructions. So our sanitization also removes any non-displayed elements.  
- **Malicious Pages:** If page is suspicious (maybe flagged by browser or contains known exploit code), agent should disable actions.  
- **Action Validation:** After click/submit, verify expected change happened (like expected new URL or DOM change). If not, roll back or alert user.  
- **User Confirmation:** Always on first sensitive use-case (like “Hey, do you want me to login on this banking site?”). Because relying purely on trust is dangerous. 1Password’s advice to require confirmation before sensitive autofill is good precedent.  
- **Least Privilege:** Extension should only request needed permissions (no broad `all_urls` without reason). This limits exploitation.  
- **Audit Logging:** Keep local logs of actions (not user data, just actions). For transparency/auditors.

## 18. Technology-by-Technology Explanation

- **WebGPU:** Ye browser ka naya API hai jisse GPU compute possible hua. Hum ise AI model inference accelerate karne ke liye use karenge. WebGPU WebAssembly se 10-15x fast hota hai for big models. Safari/Firefox me recent support aa raha. (WASM fallback bhi honge).
- **WASM (WebAssembly):** C code jaise performance. ONNX Runtime Web WASM backend CPU pe run kar sakta. Agar GPU na ho, WASM me models chalenge (sadak), ya multi-threaded for some speed.
- **ONNX Runtime Web:** Microsoft ka library, ONNX models browser me run karta. Supports WebGL, WebGPU. Hum ise vision model inference ke liye use karenge.
- **Transformers.js:** HuggingFace ka JS library. Agar koi chhota NLP/vision task use karna ho (jaise sentence embedding), use kar sakte. Lekin ye CPU focus hota hai. WebGPU support thoda incomplete (needs Wasm fallback).
- **Vision Transformers / CNNs:** Ye use karenge screen understanding ke liye. Example: **MobileNet**: size ~16MB, good mobile accuracy; **YOLOv8n**: ~6MB, object detection; **EfficientNet Lite**. Hum inko ONNX me load karenge.
- **OCR (Tesseract.js):** Client-side OCR. Tesseract.js is a full JS port of Tesseract OCR. Ye images se text nikal sakta. Use for hidden text detection.
- **Regex/NER:** JavaScript regex engine built-in. NER library (e.g. [nlpjs]) for name/email detection in any extracted text.
- **Face detection:** E.g. **BlazeFace** (TensorFlow.js) ya **MediaPipe** to detect faces in screenshots for blurring.
- **DOM/Accessibility:** Browser provides **Document Object Model** (DOM) with tags. Hum isse directly query karenge. Also use **Accessibility Tree** (AOM) to get element roles and ARIA labels.
- **Extension APIs:** Chrome/Firefox ka extension system. Content scripts manipulate DOM, background/service worker handle tasks. We need `chrome.tabs.captureVisibleTab()`, `chrome.runtime.onMessage`, etc.
- **Local Redaction:** Use HTML Canvas or CSS overlay to blur/mask identified regions. Or modify DOM `value` attributes.
- **Backend (FastAPI):** Lightweight, async support, easy Python integration. Could also use Flask but FastAPI gives easier async.
- **AI Server Models:** For example, we might use [LLaVA-1] (Vision-Language with 7B params) because it's open, or [Qwen-VL] 7B for good image Q&A. These serve image context to generate text. Possibly combine with Llama2 13B for final JSON output via instruction prompt.
- **vLLM/Ollama:** If using local GPUs, vLLM is an efficient model inference library. Ollama is user-friendly but not open code. 
- **Communication:** Plain HTTPS/JSON (FastAPI + requests). Not much to discuss.

Har technology ke liye humne alternatives dekhe (React, Node, etc.) but chuna wahi jo simplest aur performance-savvy laga. React React dome extension me add complexity; Node server can but Python more ML friendly.

## 24. Training / Fine-Tuning Strategy

Option A: **Pre-trained models only.** No training, just use existing weights. Pros: fastest to get demo. Likely good enough. 
Option B: **Fine-tune existing models.** Eg. take LLaVA and fine-tune on UI-action data. Or YOLOv8 retrain on Rico forms. Would improve accuracy.
Option C: **Train new small models.** Eg. a custom PII classifier or UI detector. Time-intensive, risk of low performance.

For SIH, time is limited. A good approach: Use pre-trained vision models (MobileNet/YOLO base) and maybe fine-tune on a small UI dataset (Rico subset) if time allows. For PII detection, rule-based + regex is enough, no ML training needed. For LLM, likely use pre-trained instruction-tuned VLM. Fine-tuning a VLM on our context (screenshots with redaction) could help, but too heavy.

Thus: use Option A or B. Focus on implementing existing, maybe quick fine-tune of a small model if needed.

## 25. Performance Optimization

- **Quantization:** Convert models to INT8/INT4 to reduce size and speed up inference. ONNX Runtime Web supports quantized models. E.g. YOLOv8 int8, Transformers LLM int4. 
- **Pruning/Distillation:** If model is large, pruned version to remove redundant weights. Possibly use distillation (teacher-student) to a smaller model.  
- **Resolution Reduction:** Process smaller images (downscale screenshot) or crop only relevant UI region. Eg. OCR on clipped regions not full screenshot.  
- **ROI Inference:** Instead of full frame every time, detect where changes happened via MutationObserver; run model on that part only.  
- **Event-Driven:** Only run vision/PII on page load or user input, not continuously. Use MutationObserver to run only when relevant DOM changes.  
- **Caching:** If same UI appears, cache its perception (but page often dynamic).  
- **Frame Skipping:** If we had video (not needed here).  
- **Web Workers:** Use background web workers for parallelism if needed.  
- **WebGPU usage:** Offload matmul to GPU. Use ONNX WebGPU with multi-thread WASM.  
- **Multi-threading:** Use `SharedArrayBuffer` (with required headers) to enable ONNX multi-threaded inference in WASM.  

These will lower latency and CPU use. Example: quantizing 7B model to int4 reduced VRAM to 4-5GB, similarly save memory and speed.

## 26. SIH Evaluation Strategy

Align tests with metrics:

- **Metric 1 (Visual Accuracy 25%):** Test a suite of web pages with known ground truth of elements (e.g. “this is login button,” “these are form fields”). Measure if our agent correctly identifies clickable elements and page state. Could use dataset like ScreenSpot questions. Score = correct actions / total.  
- **Metric 2 (PII Precision/Recall 20%):** Prepare test pages containing various PII (emails, phone, names, faces, cards). Label true PII. Measure how many we detected (recall) and how many false positive. Compute precision, recall, F1. Use e.g. email/phone regex test sets and form data.  
- **Metric 3 (Redaction Precision 20%):** Check if after redaction, server still gets enough info. Harder to quantify; possibly measure if agent still completes tasks after redaction. Or test that redacted outputs remove only sensitive parts. Could quantify by measuring information retention (like Levenshtein on non-sensitive parts).  
- **Metric 4 (Resource Utilization 20%):** Profile CPU%, memory usage of extension on example tasks (DevTools). Use tools like performance monitor. Also measure model size (MB) and CPU/GPU time for inference (via benchmarks). Maybe test on mid-range laptop and record utilization.  
- **Metric 5 (Latency 15%):** Time measure from “intention signal” (e.g. user presses “AI assist”) to action completion on end page. Break it: screenshot + local inference + redaction + network + server inference + local action. Use synthetic script to automate measurement. Lower is better.

We must create benchmarks aligned to these. Possibly prepare 10 use-cases for Visual Accuracy, 10 PII examples, etc. Compute average scores.  

## 27. Benchmarking Methodology

1. **Visual Context Accuracy (25%):** Use benchmark tasks from *WebArena* or *ScreenSpot*. For each test page, specify expected outcome (e.g., click button, fill form). Run agent, check if it does correct action on the right element. Score = fraction correct. Evaluate visually whether it understood layout.
2. **PII Precision/Recall (20%):** Assemble a dataset of screenshots or DOM snippets labeled with PII. For each, run our PII detector. Compute Precision = (#detected PII that are true)/#detected, Recall = (#true PII detected)/#true. Use typical IR formula. F1. Perhaps in report we stress recall more (or average).
3. **Redaction Precision (20%):** Evaluate that after redaction, agent can still complete tasks. Possibly measure *task completion rate* on redacted images. Also inspect some cases manually to ensure no sensitive leak and no vital info lost.
4. **Resource Utilization (20%):** Use Chrome Task Manager or OS tools: Measure memory usage (MB) and CPU % during agent execution on sample tasks. Also measure model size (disk/MB). Normalize.
5. **End-to-End Latency (15%):** Instrument code to timestamp at steps (capture start, after vision, after send, after action). Present average time for full flow (ms). Aim <1000ms.

## 29. Risks and Mitigation

| Risk                                | Probability | Impact | Mitigation                                                       |
| ----------------------------------- | ----------: | -----: | --------------------------------------------------------------- |
| **PII missed (recall issue)**       | Medium      | High  | Multi-layer detection (DOM+OCR+regex). Testing on varied data.  |
| **False positive redaction**        | High        | Medium| Precision tuning, whitelist common non-sensitive terms.         |
| **Excessive redaction (info loss)** | Medium      | High  | Semantic placeholders to retain structure. Manual review.       |
| **Model too slow**                  | Medium      | High  | Optimize models (quantization), use WebGPU, event-driven triggers. |
| **WebGPU unavailable (e.g. Firefox)** | Low      | Medium| Fallback to WASM (slower). Possibly disallow heavy tasks there.   |
| **Browser compatibility issues**    | Medium      | Medium| Test on Chrome/Firefox; limit use of bleeding-edge APIs.        |
| **Server latency**                  | Medium      | Low   | Use efficient server stack (vLLM), keep payload small (sanitized DOM). |
| **VLM hallucination**               | Medium      | Medium| Constrain outputs (JSON schema), validate action plausibility.  |
| **Wrong browser action (parsing fail)** | Medium | High  | Action executor checks element existence before click; feedback loop. |
| **Prompt injection from page**      | Medium      | High  | Pre-sanitize HTML (remove hidden commands). Use explicit prompt templates. |
| **Malicious webpage content (clickjacking, UI spoofing)** | Medium | High | Validate element visibility, require user confirm for crucial actions. |
| **Data exfiltration by extension**  | Low         | High  | Limit permissions, do not store user data locally.             |
| **High memory use (extension)**     | High        | Medium| Use lightweight models, unload after use, watch memory.        |
| **OCR errors**                      | High        | Medium| Use confidence threshold, fallback to regex, allow manual review. |
| **Dynamic DOM changes**             | High        | Medium| Use MutationObserver to re-run pipeline on changes.            |
| **Cross-origin frames**             | Medium      | Low   | Skip cross-origin or warn user (can't access iframe content).   |

Probability/Impact subjectively. Mitigations focus on redundancy, user in loop, error checks.

## 30. Development Roadmap

- **Phase 1: Extension Skeleton.** Set up Chrome extension manifest V3, background worker, content script injection. Basic permissions (activeTab). *Why:* Foundation to build. *Output:* empty extension that can capture DOM. *Problems:* MV3 learning curve, permission issues.
- **Phase 2: DOM Extraction.** Content script grabs visible DOM structure and sends to background. *Why:* Baseline context. *Output:* JSON of elements and text. *Dependencies:* None major. *Problems:* Getting bounding boxes (might use Element.getClientRects).  
- **Phase 3: Screenshot Capture.** Use `chrome.tabs.captureVisibleTab` to get screenshot image. Send to content script (as data URL). *Why:* Needed for vision/vision-based PII detection. *Problems:* Cross-origin restrictions, large data URL length.
- **Phase 4: Basic PII Detection.** Implement regex/DOM rules. E.g. find `<input type="password">` and mark, regex for `\d{10}` phone etc. *Why:* Privacy core. *Output:* highlighted elements. *Problems:* Regex false alarms, test on multiple pages.
- **Phase 5: Redaction Engine.** Given detected PII regions, apply blur/mask on screenshot or overlay on DOM. *Why:* Show privacy functionality. *Output:* Sanitized image. *Problems:* Performance of canvas blur; ensure still readable layout.  
- **Phase 6: Local Vision Model Integration.** Add ONNX model (say YOLOv8 nano) via ONNXRuntime-Web. Load in extension and run on screenshot to detect UI elements. *Why:* See local ML inference work. *Output:* Detected bounding boxes for UI. *Problems:* Model loading time, WebGPU support.
- **Phase 7: Backend Setup.** Create simple FastAPI server stub. One endpoint /analyze: get sanitized context, return JSON action (hardcode a response). *Output:* working client-server comm. *Problems:* CORS permission, extension networking.
- **Phase 8: Basic VLM Integration.** Replace stub with call to VLM (HuggingFace or local LLaVA via Python). Provide prompt template for action. *Output:* server actually reasons about action. *Problems:* Model loading, prompt design, JSON formatting.
- **Phase 9: Action Generation & Execution.** Parse server JSON response, map target to DOM selector (e.g. find button by text), and perform action. Test with simple forms. *Output:* End-to-end action cycle. *Problems:* selector matching errors, dynamic pages.
- **Phase 10: Security Layer.** Implement local policy checks (e.g. confirm on login). Sanitize any server output if needed. *Output:* safe auto-UI. *Problems:* UX flow for confirmations.
- **Phase 11: UI/Feedback.** Add extension UI to trigger agent and display status. *Output:* user control. *Problems:* time.
- **Phase 12: Testing & Benchmarking.** Create test cases, measure metrics, optimize. *Output:* Report metrics. *Problems:* Good dataset preparation.
- **Phase 13: Demo polish.** Prepare final use-case flows for SIH demonstration. *Output:* cohesive demo scenarios. *Problems:* Dry-run check.

Plan may be adjusted as hurdles appear, but aim for core demo by mid-development and polish.

Jaise hi user koi web page open karta hai, extension us page ka **DOM structure aur screenshot** capture karta hai. Phir **local AI model** (Vision Transformer ya MobileNet) page ko samajhta hai: kaunse buttons, text fields hain, etc. Saath hi **PII-detection engine** page me sensitive cheezon ko dhoondta hai – jaise passwords, emails, phone, ya faces. Ye cheezein milte hi *blur/pixelate* ya `[EMAIL]`, `[PHONE]` jaise placeholders se mask ho jati hain. Sirf ye sanitized (non-sensitive) context hi server ko bheja jata hai.

Server pe **vision-language model** (jaise LLaVA ya Qwen-VL) use karke page ka context samjhaya jata hai. Model ko bataya hota hai ki masked fields ke jagah kya placeholder diye gaye hai. Fir model decide karta hai ki agla action kya hoga (jaise “Submit button click karo” ya “Email field me type karo”). Ye answer hum **structured JSON** me bhejte hain (for example `{"action":"click", "target":"login_button"}`). Browser extension fir is action ko parse karke page pe apply karta hai (target element dhundh ke click ya type karta hai).

Is solution ka fayda: **Privacy** – user ka asli data browser ke bahar nahi jata; **Speed** – local inference se kam latency hoti hai; **Accuracy** – DOM + vision se page achhi tarah samjha jata hai; **Safety** – sensitive fields automatically cover ho jati hain aur ham local policies se secure karte hain.

Har important tech term:

- **WebGPU:** Ek naya browser API hai jo GPU (graphics card) ko use karke AI models ko fast chalata hai. Hum ise inference ko tez karne ke liye istemal karenge.  
- **ONNX Runtime Web:** Microsoft ki library hai, jo ONNX-format models ko browser me chalane deti hai. Isme WebGPU/WebWASM backend hota hai.  
- **Transformers.js:** HuggingFace ka JS library hai, lekin hum mainly ONNX use karenge kyunki hum larger models chalayenge.  
- **Vision Transformer (ViT):** Ye ek neural network architecture hai jo images ko tokens me tod ke process karta hai. Hum iske lightweight versions use karenge for screen images.  
- **OCR (Tesseract.js):** Ye ek JS library hai jo image se text nikalti hai. Hum ise use karenge jahan image me text ho (jaise docs ya numbers).  
- **PII:** Stands for *Personally Identifiable Information*. Jaise aapka naam, phone, email, Aadhaar number, faces. Ye detect karke hi server ko bheja jayega.  
- **JSON schema:** Structured format me action return karna. Yeh ensure karta hai ke LLM ka answer easily parse ho sake.  
- **DOM:** Webpage ka structure (HTML elements). Hum DOM se page ke fields aur buttons find karte hain.

Yeh system design karne se hum ISRO ke SIH criteria sab me ache score layenge: screen context sahi identify karenge, PII detection accurate hogi, redaction precise hogi, client resources optimize honge aur latency kam rahega. Hum real use-cases (login, form-fill, navigation) dikhayenge, jahan extension PII ko pehle mask karta hai, phir sahi action server se laake page pe perform karta hai. Judges ko clear visible hoga ki sensitive data kabhi server tak nahi gaya, sab local hi handle hua.

## If I Were Building This for SIH — My Final Recommendation

Main architecture as per final design chununga: Hybrid DOM+Vision pipeline inside browser extension, multi-stage privacy engine, structured JSON actions, lightweight models, and local policy checks.  

- **Best Architecture:** DOM + Accessibility tree for element info, selective screenshot for hard cases + local vision model (via ONNX & WebGPU) and multi-layer PII detector. Server receives sanitized structured context (no raw screenshot).  
- **Privacy Strategy:** Multi-layer PII detection (DOM tags + regex/OCR + face detection) with contextual masking (e.g. replace name with [NAME]). This ensures 0% raw PII leaks. Use contextual masks to preserve semantics.  
- **AI Models:** On-device: YOLOv8 Nano (ONNX) for UI, Tesseract.js for OCR, Tiny face model. Backend: Qwen-2.5-VL or LLaVA-2 (7B) for image understanding, combined with a 13B Llama2-like model for JSON action output. Quantize models to int8/4 where possible for efficiency.  
- **USP:** Privacy-first pipeline with local redaction is key differentiator. Emphasize hybrid DOM+vision perception.  
- **Demo Strategy:** Show login and form examples: highlight how sensitive fields are auto-masked. Judges see agent working *without* showing any real private data.  
- **Implementation Priority:** First get core loop (capture DOM/screenshot → mask → send → get JSON → execute) working with dummy server. Then integrate ML detection gradually (PII detection and vision). Optimize with WebGPU. Add security checks last.

Yeh design SIH evaluation ke 5 metrics me high rank laayega: high accuracy of screen understanding (hybrid method), high PII recall (multi-layer detection) aur precision (smart masking), optimized resource use (light models, WebGPU), aur low end-to-end latency (minimal data, local compute).  

**Banaye rakhein:** Always end-to-end demo with real sensitive example (like banking login). Phir judges ko batayen how each step preserve privacy. Humara solution unique hai kyunki hum “har cheez browser me handle karte hain, server se sirf safe info share hoti hai” (Hindi: “Sab kuch local hi hota, server tak bas safe data hi jata hai”).  

**Final Note:** Upar diye sare references aur analysis ka core message yeh hai ki jab AI agent browser me chal raha ho, privacy sabse pehle rakhna padega. Aur humari hybrid approach is test case ke liye ek strong, buildable architecture provide karti hai.
